CACSMS SPORTS — Technical Implementation Specification
We will proceed with the detailed implementation specification for the rebuilt platform, covering the exact folder structure, navigation routes, responsive application shell, engine contracts, PostgreSQL database architecture, APIs and autonomous operating workflows.

This specification establishes the development blueprint. It does not assume that any of the new components have already been implemented.

Non-negotiable design principles
Every engine has one clearly defined responsibility.

All engines communicate through typed contracts and versioned events.

PostgreSQL is the authoritative operational database.

Research evidence must exist before a prediction can be qualified.

Qualification cannot be bypassed by tickets, programmes or booking-code services.

Models must pass independent validation before activation.

The interface must show actual operational states, not simulated production metrics.

Every external action must be traceable, idempotent where possible and governed by explicit policies.

The engines directory contains reusable business logic. The workers directory contains asynchronous execution adapters. The apps/api directory exposes validated operations to the frontend.

For example, the Research Engine should not depend on Celery directly. Its worker calls the engine and publishes the resulting event. This makes the research logic independently testable.

Required database constraints
fixtures: unique canonical fixture identity, with provider mappings stored separately.

source_observations: unique source observation identity or content hash, with immutable collection timestamps.

research_dossiers: versioned by fixture and research revision.

predictions: immutable forecast version, model version, feature snapshot and prediction timestamp.

odds_snapshots: bookmaker, event, market, outcome, price and observed timestamp.

qualification_decisions: immutable gate evaluation referencing exact forecast and price versions.

ticket_legs: foreign keys to qualified opportunities and their qualification versions.

booking_codes: uniqueness scoped to the bookmaker and verified external code.

settlements: idempotent settlement key, official result reference and correction history.

audit_events: append-only audit records with actor, action, correlation ID and timestamp.

Financial history from the existing system should be preserved separately from model-performance records. Historical corrections must not erase original transactions or settlement evidence.

Administrative mutation endpoints should be separate, role-restricted, authenticated and audited. No generic API endpoint should accept an arbitrary qualified=true flag or directly convert a proposed ticket into a paid wager.

Real-time event channels
Use server events for:

mission.updated, fixture.discovered, research.completed, prediction.created, qualification.decided, ticket.prepared, booking_code.verified, settlement.completed, incident.opened, and worker.health_changed.

Every event should contain a schema version, event ID, correlation ID, timestamp and source engine. Consumers must tolerate duplicate delivery.

The mission controller should support:

Distributed worker leases with expiry and heartbeat.

Unique idempotency keys per fixture, market, model and processing version.

Retry limits and exponential backoff.

Dead-letter queues for jobs requiring investigation.

Independent source and model circuit breakers.

Explicit timeout, cancellation and recovery states.

Versioned workflow definitions and audit histories.

An external booking-code request requires an additional reconciliation step before retrying, to prevent duplicate operations when a browser action succeeds but its acknowledgment is lost.

WP-02

WP-03

Autonomous Mission Control

Schedulers, workers, queues, engine orchestration and recovery

WP-04

Sports Discovery & Deep Research

WP-05

Prediction & Model Intelligence

Features, sport-specific models, calibration, validation and governance

WP-06

Markets & Qualification

Odds verification, market mapping, expected value and mandatory gates

WP-07

Strategy Programmes

Accumulator, Singles, Jackpot, Draw and Rollover engines

WP-08

Tickets & Booking Codes

Ticket optimization, betslip preparation, code retrieval and verification

WP-09

Results & Continuous Learning

Official results, settlements, prospective evaluation and model monitoring

WP-10

Diagnostics, Migration & Release

Monitoring, data reconciliation, end-to-end tests, deployment and rollback

Implementation controls
Each work package must deliver complete source code, migrations where applicable, automated tests, API documentation, responsive interfaces and verified operational evidence.

WP-01 and WP-02 are the foundation. The later work packages should be integrated incrementally, rather than built as disconnected applications and joined at the end.
